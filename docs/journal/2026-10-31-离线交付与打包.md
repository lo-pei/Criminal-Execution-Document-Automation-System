# 2026-10-31 · 离线交付与打包链路

> 触发：业务方补充「法院电脑都在内网，不联网，连基础环境都下载不了」。
> 本条目记录该约束引发的设计变更、实测结果与踩到的坑。前一条见 [`2026-10-31-项目启动.md`](2026-10-31-项目启动.md)。

## 1. 这条约束改了什么

原计划把「目标机安装 Python + 依赖」当作可接受前提，只需打包成 exe 即可。内网无网后，
这个前提不成立，结论升级为：**目标机零安装，构建机承担全部下载与编译**。

连带三处必须调整：

1. 交付形态定为 **onedir**，推翻需求文档建议的 onefile（理由见 ADR-010）。
2. `config.py` 的路径模型必须重做——见下节，这是本次最重要的发现。
3. 规则必须能在不重新打包的前提下升级，否则内网每改一条规则都要重走拷贝审批。

## 2. 发现并修复的缺陷：打包后数据会丢

`config.py` 原用单一 `ROOT_DIR` 同时承载资源与数据：

```python
ROOT_DIR = _locate_root()          # 打包后 = sys._MEIPASS
DATA_DIR = ROOT_DIR / "data"       # ← 临时解包目录
DB_PATH = DATA_DIR / "cedas.db"
```

`sys._MEIPASS` 在 onefile 下是 `%TEMP%\_MEIxxxx`，在 onedir 6.x 下是 `_internal`，
两者在程序退出后都可能被清理。后果是**台账数据库与生成的文书落进临时目录，一关程序全没了**。

在「生成文书就是交付物」的场景下这是数据丢失级缺陷，而且开发期完全看不出来——
只有打成包跑一次才会暴露。修复方式见 ADR-011：拆 `BUNDLE_DIR`（只读）与 `APP_HOME`（可写）。

**教训**：凡是「打包后才跑得到」的路径，在写第一行代码时就该按只读/可写分开设计，
而不是等打包时再补。

## 3. 实测数据

在开发机（Win11 / AMD64 / Python 3.14.4）上完成构建：

| 项 | 结果 |
|---|---|
| 构建耗时 | 约 48 秒（含冒烟测试） |
| 产物 | 1020 个文件，87.5 MB |
| 交付 zip | 46.3 MB |
| 冒烟测试 | 通过（`cedas-cli doctor --json`，`ok=true`，`rule_count=2`） |
| 体积构成 | PyMuPDF 及其扩展约 53 MB，其余为 CPython 运行时与 Tcl/Tk |

**注意**：3.14 不是推荐的交付解释器。`requirements-build.txt` 与文档建议 3.11/3.12，
理由是老旧 Win10 缺 UCRT 补丁时可能启动失败。本次用 3.14 只是为了验证链路。

尚未验证：目标机（4GB 内存 / 旧 CPU）上的冷启动、单份耗时、内存峰值。**这是下一项必做实测。**

## 4. 这次踩到的五个坑

1. **构建机是精简版 Python，没有 tkinter。** `import tkinter` 直接失败，而 PyInstaller
   对此一路放行，打出的 exe 双击无界面、无任何报错。已固化为构建脚本的前置闸门。
2. **PyInstaller 产物输出恒为 GBK。** 即便显式设置 `PYTHONUTF8=1` 与
   `PYTHONIOENCODING=utf-8`，子进程的管道输出仍是系统代码页——bootloader 会重置 stdio。
   冒烟测试最初按中文标记匹配，因此在构建机上「莫名失败」。改为只认 JSON 里的
   布尔与数值字段，解码按 utf-8 → gbk → mbcs 依次回退。
3. **PyMuPDF 2.0 连带安装 `pymupdf4llm` / `pymupdf_layout` / `onnxruntime`。**
   包体积会莫名膨胀数百 MB。锁 `pymupdf<2`，并在 spec 中显式 exclude。
4. **`--clean` 触发批量删除保护。** 一次删除上千个文件被环境策略拦下，表现为构建无理由失败。
   改为「移开旧产物」而非删除，顺带保留了上一版便于比对体积。
5. **交付 zip 没有版本目录前缀。** 用户解压到桌面时上千文件直接铺开，找不到 exe。
   已修正为固定带一层 `CEDAS-<version>-win64/`。

`.gitignore` 里的 `*.spec` 一度把 `packaging/cedas.spec` 也忽略了，已加例外。
