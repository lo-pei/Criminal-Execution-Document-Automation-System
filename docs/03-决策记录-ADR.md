# 03 · 决策记录（ADR）

> 只追加，不删改。推翻旧决策时新增一条并标注 `Supersedes: ADR-XXX`。
> 格式：背景 → 决策 → 理由 → 代价 → 状态。

---

## ADR-001 · 运行端不部署任何模型

**状态**：已采纳（2026-10-31）

**背景**：需求方希望在离线程序内提供「智能补抽」以覆盖规则漏字段。

**决策**：v1 运行端零模型。抽取只走规则锚点。保留 `Extractor` 协议接口，不实现具体模型。

**理由**：
1. 字段位置由法定文书格式决定，锚点稳定，规则的命中成本低于生成式模型。
2. 目标机 4GB 内存，小模型 CPU 推理即需 ≥2GB 常驻，与 Word/WPS 同时打开必然换页。
3. 生成式抽取在不容错的刑事文书场景中可解释性不足——无法回答「这个值从哪来」。

**代价**：规则覆盖不到的变体需人工补录。已由「漏字段清单 + 复核队列」承接。

## ADR-002 · 规则库外置为 JSON，程序只保留执行器

**状态**：已采纳

**背景**：规则会持续膨胀，若编进代码，每次增补都要重新打包发布。

**决策**：规则以 JSON 存于 `resources/rules/`，程序只实现加载、匹配、装配。复杂逻辑（如日期拼接）以少量 Python 函数实现，由 JSON 以 `handler` 字段引用。

**理由**：现场可替换 JSON 完成规则升级，不必重打包；规则可被非开发者审阅。

**代价**：JSON 无法表达复杂逻辑，需 handler 机制兜底；规则与代码存在版本耦合风险，故启动时校验 schema 版本。

## ADR-003 · 界面用 Tkinter，不用 PySide6

**状态**：已采纳

**背景**：底座项目参考方案用 PySide6。

**决策**：Tkinter + ttk。

**理由**：
1. 体积：PySide6 使安装包增加约 150MB、常驻内存增加约 100MB，与「低占用」目标冲突。
2. 兼容：若目标机存在 Win7，Qt6 直接不可用；Tkinter 无此问题。
3. 溯源展示用 `Text` + `tag` 已足够实现「点击字段高亮原文段落」。

**代价**：界面观感朴素；复杂表格需自行封装 `ttk.Treeview`。

## ADR-004 · 采用 PyMuPDF，并登记 AGPL 风险

**状态**：已采纳，附交付前复核条件

**背景**：候选为 PyMuPDF / pdfplumber / pdfminer。

**决策**：PyMuPDF（`fitz`）。用 `page.get_text("dict")` 按块提取，保留 bbox 与字号。

**理由**：文本提取速度与内存占用均优于另两者；`dict` 模式提供版式信息，是页眉页脚判定与段落重建的前提。

**代价与风险**：**PyMuPDF 为 AGPL-3.0**。院内自用不构成分发，不触发开源义务；一旦向其他单位交付，须开源本项目或购买商业许可。

**交付前必查**：交付范围是否超出本单位自用。此项列入发布检查单。

## ADR-005 · 双通道输入：PDF 为生产，TXT 仅开发

**状态**：已采纳（2026-10-31，业务方确认）

**背景**：因保密要求，开发阶段只能获得人工从 PDF 全选复制得到的 TXT；生产环境仍处理 PDF。

**决策**：两条通道并存，共用同一清洗层。
- `ingest/pdf_reader.py`：生产通道，唯一可交付路径。
- `ingest/txt_reader.py`：开发通道，仅用于规则编写与回归，**不得出现在生产流程中**。

**理由**：若为 TXT 单独写一套清洗逻辑，规则会在两套实现间漂移，在 TXT 上验证的结论对 PDF 无效。

**代价（必须承认的能力降级）**：
1. `page` 恒为 `None`，溯源降为段落级。
2. 无字号 ⇒ 标题判定退回启发式。
3. 无坐标 ⇒ 页眉页脚只能用「跨页重复率」判定，位置判据无法在 TXT 上验证。

**缓解**：样本保留原始噪声（不手工清理页眉页脚）；尽早打通 PDF 通道并在真 PDF 上回归，将「PDF 回归通过」设为阶段 2 的退出门槛。

## ADR-006 · 刑期届满日 = 起算日 + 刑期 − 1 日

**状态**：已采纳，月末情形待业务确认

**背景**：刑期起止日算法存在两种常见写法，差一天。

**决策**：`届满日 = 起算日 + N年M月 − 1日`，`释放日 = 届满日 + 1日`。月运算按日历推进，目标月无对应日时取该月最后一日，再减 1 日。

**理由**：刑期含起算日当日（羁押一日折抵一日）。四年有期徒刑自 2023-01-01 起算，届满日为 2026-12-31，而非 2027-01-01。文书实务亦按此表述。

**待确认**：起算日为月末日时的减 1 日约定（如 1 月 31 日起算一个月 → 2 月 27 日或 28 日）。当前实现取「月末日再减 1 日」，已记入 spec 待确认事项。**在业务方确认前，该边界用例不得作为验收依据。**

## ADR-007 · 溯源定位到段落，不做字符级偏移

**状态**：已采纳

**背景**：需求要求「每个字段能定位到原文出处（页码、段落）」。

**决策**：`Provenance(page, paragraph_index, snippet)`。不存字符级偏移。

**理由**：字符级映射要求清洗过程全程维护偏移表，任何一条规范化规则改动都会使映射失效，维护成本远高于收益。段落级已能满足「人工复核时高亮定位」。

**代价**：长段落内的精确定位依赖 `snippet` 文本匹配，而非坐标。

## ADR-008 · v1 不打包兜底模型

**状态**：已采纳（推翻原始需求「可选兜底」的实现方式）

**背景**：原方案建议 RexUniNLU / UIE-nano 作为规则漏字段时的补抽手段，按需触发。

**决策**：v1 不引入。仅保留 `Extractor` 协议，第三方实现可插拔。

**理由**：打包体积增加数百 MB；CPU 推理需 ≥2GB 内存；「低置信度 → 人工确认」的价值可由「漏字段清单 + 手工补录」等价实现，成本低一个数量级。

**代价**：极端格式变体只能人工处理。

## ADR-009 · 垂直切片优先于横向全量

**状态**：已采纳

**背景**：原始计划按阶段 0→6 横向推进（先全量清洗，再全量抽取，再全量映射）。

**决策**：先以「1 法院 + 执行通知书 1 类 + 20 份样本」打通端到端，再横向扩模板与法院。

**理由**：字段字典与模板映射的真实耦合关系，只有在端到端跑通一次后才暴露。横向推进会把这类问题积压到阶段 4 集中爆发。

**代价**：首期覆盖面窄，需向业务方管理预期。

## ADR-010 · 交付形态为 onedir 目录包，目标机零安装

**状态**：已采纳（2026-10-31，因「内网不能下载基础环境」确认）

**背景**：目标机位于法院内网，不联网，无法下载 Python、运行库或任何依赖；需求文档原建议 PyInstaller 单文件 EXE。

**决策**：
1. 构建在有网的构建机上完成，产出 **onedir 目录包** + zip，通过介质送入内网。
2. 目标机不安装任何东西：解释器、Tcl/Tk、全部第三方库随包分发，双击即用。
3. **不用 onefile**（推翻需求文档的建议，理由见下）。

**理由**：
- 目标机零安装是「内网无网」唯一可行的形态。任何形式的环境准备（装 Python、装 VC++ 运行库、配 pip 源）在内网都不可执行。
- 放弃 onefile 的三条理由会直接导致部署失败：① 法院终端管控常禁止从 `%TEMP%` 执行二进制，onefile 每次启动都解压到 `%TEMP%`，表现为**双击无反应且无报错**；② 本项目解压量 100MB+，老机械硬盘上 onefile 冷启动 5–15 秒；③ 自解压行为易被杀毒软件判为投放器。
- `upx=False`：UPX 压缩会显著提高误报率，体积收益不值得用部署失败去换。

**代价**：
1. 产物是目录而非单文件，交付时须打 zip 并说明「解压后整个目录一起用」。
2. 构建机必须是有网、64 位、**完整安装（含 tcl/tk）**的 CPython。精简版 Python 打出的 exe 无界面且打包阶段不报错——该检查已固化为构建脚本的前置闸门。
3. 无法在线更新，每次程序升级仍需人工拷贝（规则可现场替换，见 ADR-011）。

**验证**：`tools/build_offline.py` 在打包后立即运行产物内的 `cedas-cli doctor --json` 做冒烟测试，失败即不产出交付包。

## ADR-011 · 只读资源与可写数据分离；规则按文件名两层覆盖

**状态**：已采纳（2026-10-31，修正 `config.py` 的缺陷）

**背景**：`config.py` 早期用单一 `ROOT_DIR` 同时承载资源与数据。打包后 `sys._MEIPASS` 指向解包目录（onefile 为 `%TEMP%\_MEIxxxx`，onedir 6.x 为 `_internal`），该目录内容在退出后可能被删除。后果是**台账数据库与生成文书写入临时目录，程序一关即丢失**——在「生成文书是交付物」的场景下属于数据丢失级缺陷。

**决策**：
1. 拆为 `BUNDLE_DIR`（只读资源，取 `_MEIPASS`）与 `APP_HOME`（可写数据，取 exe 所在目录，可用环境变量 `CEDAS_HOME` 覆盖）。
2. 规则加载改为多目录按优先级合并：`<只读>/resources/rules` 为基线，`<可写>/resources/rules` 为现场补丁区，**同名文件整体覆盖**。

**理由**：
- 只读与可写混用在任何打包形态下都是错的，只是内网部署把它放大成不可接受的后果。
- 数据不落 `%LOCALAPPDATA%`：法院要求归档文件在固定盘符、同事可见可备份，藏在用户目录里等于找不到。
- 规则按「文件」而非「rule_id」覆盖：否则「基线有、补丁删」无法表达，规则库会退化成无法推理的叠加层。
- 不直接改 `_internal/resources`：那是安装产物，用户改动无记录、易被下一次覆盖抹掉；exe 旁的 `resources/` 是显式补丁区，备份回滚都直观。

**代价**：
1. 多一个可写目录需要解释，已写入交付包内的 `离线安装说明.txt`。
2. 规则补丁文件名必须与基线同名才覆盖，命名错误会变成「新增一条规则」而非替换——已在文档与加载器的重复 `rule_id` 检查中双重拦截。

## ADR-012 · 构建机使用版本固定的干净虚拟环境

**状态**：已采纳

**背景**：实测在装有 PyMuPDF 2.x 周边包（`pymupdf4llm`、`pymupdf_layout`，连带 `onnxruntime` 与 `numpy`）的机器上打包，这些包会被依赖分析顺带拉入，体积与打包时间同时失控。

**决策**：`requirements-build.txt` 固定运行依赖与 PyInstaller 版本；spec 中显式 `excludes` 上述重包；构建脚本检测到污染环境时给出提示。

**理由**：交付物的内容应当由清单决定，而不是由「构建机上恰好装了什么」决定。同一份源码在不同机器上打出不同体积的包，会让内网审计无法复现。

**代价**：升级依赖需人工改清单并重新验证，不能 `pip install -U` 了事。这是有意的。

## ADR-013 · 解释器降到 Python 3.8，一份包覆盖 Win7 与 Win10

**状态**：已采纳（2026-10-31，业务方确认「有 Win7 机器需要兼容，且需全功能」）

**背景**：ADR-010 的方案按 Python 3.9–3.12 设计。业务方随后确认目标机含 Windows 7。
**CPython 3.9 起不再支持 Windows 7**，3.8.10 是最后提供 Windows 安装包的版本。
这一步若判断错，整个技术栈要重做，且无法在后期补救。

**决策**：
1. 解释器锁 **CPython 3.8.10**，产出**一份包**，同时覆盖 Win7 与 Win10。
2. `pyproject.requires-python` 下界改回 `>=3.8`；ruff `target-version = "py38"`；mypy `python_version = "3.8"`。
3. 依赖随之降档：`pymupdf==1.23.26`、`python-docx==1.1.2`、`MarkupSafe==2.1.5`、
   `pyinstaller==6.10.0`（均已用 `pip download --python-version 38` 实测有 cp38 轮子）。
4. 构建脚本增加目标 profile（`win7` / `win10`），版本不符直接拒绝构建；
   验证链路时可加 `--allow-unsupported-python` 绕过，但产物名会标 `-unsupported` 且 SBOM 标记 `deliverable: false`。

**理由**：
- **不做双包**。双包意味着两套依赖锁定、两套回归、两次分发，规则库还要双向同步；
  内网环境里每多一份产物，就多一个「现场用的是哪一版」的争议。
- 代码本来就没用 3.9+ 特性：无 `match`、无 `slots=True`、无 `StrEnum`、无 `functools.cache`，
  且所有业务文件均有 `from __future__ import annotations`，`list[str]` 注解在 3.8 不会求值。
  经 `ast.parse(feature_version=(3,8))` 全量校验，语法层面零不兼容。
- 3.8 在 Win10 上运行正常，代价只是性能低 10–25%。对「目标 <30 秒」的单份文书处理，可接受。

**代价（必须向业务方说明）**：
1. **Python 3.8 已于 2024-10 停止维护**，不能靠升级依赖修安全漏洞。内网离线环境不涉及在线攻击面，
   但这意味着将来遇到依赖漏洞只能升解释器，而升解释器就等于放弃 Win7。
2. `pymupdf` 停在 1.23 分支，新特性用不上（当前只需要 `get_text("dict")`，功能足够）。
3. **Win7 机器往往更老**，内存可能只有 2GB。故内存预算由 4GB 下调为「按 2GB 设计」，
   界面须避免一次性加载全部台账与全文高亮。
4. 构建机必须装 Python 3.8.10。用其它版本构建会被闸门拒绝（或用 `-unsupported` 标记为不可交付）。

**退出条件**：全部 Win7 机器退役后，改用 `requirements-build-win10.txt` + `--target win10`
重新构建，即可切回 3.11/3.12。两份配方功能完全一致，代码无需改动。
