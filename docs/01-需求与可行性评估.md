# 01 · 需求与可行性评估

> 本文记录原始需求的审计结论。**结论已生效，后续开发不得基于被否决的假设。**
> 最后更新：2026-10-31

---

## 1. 原始需求摘要

法院内网、全程离线的刑事执行文书自动制作系统。操作人员上传刑事判决书（带文本层 PDF，非扫描件），系统抽取关键信息，填入预设执行文书模板，生成文书并对原始材料与生成件规范命名、归档、统一管理。

四类字段：A 组（标识与主体）、B 组（定罪与量刑）、C 组（刑期计算）、D 组（程序性字段，本项目新增）。

部署约束：无 GPU、纯 CPU、目标机内存可达 4GB、一键安装、不依赖任何云服务。

开发约束：由 Agent 辅助编写与迭代，用脱敏样本提升离线程序抽取能力，**交付物运行时不部署任何大模型**。

## 2. 总体判断

**「运行端零模型 + 规则锚点抽取」的架构判断成立，可以直接开工。**

依据：刑事判决书的字段位置由法定文书格式决定，集中在首部、主文、落款三处，锚点稳定；相较生成式抽取，规则层在不容错的刑事场景中可解释、可回归、可审计，且零推理开销。本地 LLM 的硬件需求与「旧机一键部署」直接冲突。

## 3. 审计出的八处缺陷

按造成返工的严重程度排序。前两条是**模型级**问题，不定则阶段四全线返工。

### 3.1 生效日期不在判决书中（结构缺口）

执行通知书与结案登记表均需「判决生效日期」，但判决书只写「如不服本判决，可在接到判决书第二日起十日内提出上诉」。该字段必须以独立入口录入或推算，**不可能从文本抽取**。

→ 处置：新增 D 组，共 10 个程序性字段。见 `00-字段字典-spec-v0.1.md` §4。

### 3.2 罪名与刑期不是标量（结构缺口）

数罪并罚案件中，一名被告人有多个罪名、分别量刑，再加一个「决定执行」的合并刑期。原始需求把「罪名、主刑刑种与刑期」当作单个字段，遇到数罪并罚即失效。

→ 处置：改为 `crimes[]`（各罪）+ `merged_sentence`（决定执行）两级结构。

### 3.3 C 组起止日是「计算 + 校验」而非「抽取」

两个理由：其一，取保候审、监视居住的被告人判决书中没有起止日，起算日是交付执行之日；其二，即便抽到「自 X 年 X 月 X 日起至 X 年 X 月 X 日止」，也必须验算，不能直接采信。

→ 处置：内建刑期计算器；抽到的文本起止日仅作校验输入。

### 3.4 案号正则过窄

原式 `（\d{4}）[^）]{1,6}刑初\d+号` 漏掉：法院代字实际形态（京0105、粤0305）、铁路运输法院（铁刑初）、少年庭（少刑初）、案件类别（刑终/刑再/刑更/刑抗，二审判决同样进执行）、全半角括号混用。

→ 处置：放宽为 `[（(]\s*\d{4}\s*[）)]\s*[^）)]{1,10}?刑(初|终|再|更|抗)\s*\d+\s*号`。

### 3.5 多被告人切分键选错

单靠「被告人」二字切分，会在事实叙述段（「被告人供述」「被告人张某到案后」）误切。

→ 处置：双锚定——主文区间内「一、二、三、」分项编号 + 其后紧跟「被告人 X 犯…罪」，两者同时命中才切。

### 3.6 页眉页脚「位置 8%」单条件会误伤

两页的短文书用纯位置法必删正文首行；多页密集排版时首部法院名称亦可能落在顶部区间。

→ 处置：改为「位置区间 + 跨页重复率 ≥50%」双条件；单页仅出现一次且字号 ≥ 正文 1.2 倍者一律保留。

### 3.7 模板占位符会被 Word 拆成多个 run

在 Word 中手打 `{{被告人}}` 后再编辑，字符会分散到多个 run，docxtpl 匹配失败，现场表现为「生成成功但占位符还在」。

→ 处置：模板导入时做 run 合并预处理 + 未解析占位符校验器；表格型模板走逐格填充。

### 3.8 命名规则缺唯一性与非法字符处理

案号含全角括号可保留，但罪名、被告人可能含 `/ \ : * ? " < > |`；同案多人多文书需保证唯一。

→ 处置：`案件目录/{案号}/{被告人}/{文书类型}_v{n}_{yyyyMMdd}.docx`；DB 存相对路径 + 内容哈希；防 Windows 260 字符路径上限。

## 4. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 运行端部署 7B 级 LLM | 4-bit 量化后 4–5GB，与 4GB 目标机冲突 |
| 运行端部署 RexUniNLU / GAVEL-NER 兜底 | CPU 模式需 ≥2GB 内存，且 torch 打包使安装包增至数百 MB；收益可由「漏字段清单 + 人工补录」低成本等价实现 |
| OCR 视觉模型 | 输入为带文本层 PDF，引入即增加体积与失败面 |
| MySQL / PostgreSQL | 单机单用户，SQLite 零配置即可 |
| 用无标注文本训练抽取模型 | 无标注即无监督信号；且训练与运行是两件事，训练侧不解决运行侧需求 |

## 5. 已确认的边界（业务方 2026-10-31 决策）

| 决策项 | 结论 |
|---|---|
| 目标环境 | Win10；WPS 与 Office 并存，**版本低、启动慢** |
| 交付节奏 | 垂直切片优先：1 法院 + 执行通知书 1 类 + 20 份样本端到端 |
| 界面形态 | Tkinter（非 Qt） |
| 生效日期 | 人工录入，系统据以计算起止日 |

## 6. 由此产生的三条硬约束

1. **生成链路完全脱离 Office。** 不调 `win32com`、不起 Word/WPS 后台进程，纯 `python-docx` / `docxtpl` 写 OOXML。代价：无法调用 Office 做 PDF 导出与版式校验，程序只保证值与结构正确。
2. **模板必须 `.docx`。** `.doc` 需用户另存，或做一次性 COM 转换。
3. **预览不借外部程序。** 复核界面用 Tkinter `Text` + `tag` 自绘高亮，同时满足「字段可定位到原文」的要求。

## 7. 结论

需求可执行，但必须按本文件的修正意见实施。**三份文件构成开发基线**：本文件（约束）、`00-字段字典-spec-v0.1.md`（数据契约）、`02-系统架构.md`（实现结构）。三者冲突时，以字段字典为准。
