# 09 · 端到端渲染与归档

> 一句话：`cedas render` 把「判决书进」到「执行文书出」串成一条命令。
> 本文记录一条数据在每层被改了什么、哪里会阻断、哪里还留着坑。

---

## 1. 链路

```
判决书.pdf ──ingest.read_document──▶ RawBlock[] ──clean──▶ ProseParagraph[]
                                                                    │
                                                             extract│
                                                                    ▼
                                                    Case + Defendant[]（含刑期区间）
                                                                    │
                                    ┌───────────────────────────────┘
                                    ▼
                            pipeline.generate（本文）
                                    │
        ┌───────────────┬───────────┴──────────┬─────────────────┐
        ▼               ▼                      ▼                 ▼
  calc.resolve_span  render.build_context  storage.archive   storage.db
  起算日 → 届满日     字段 → 占位符        命名 + 版本号      台账 + sha256
                                    │
                                    ▼
                        执行通知书.docx（归档目录下）
```

**分层边界**：`pipeline` 是唯一知道「一份判决书要出几份文书、每份叫什么名字」的地方。
`extract` 只认识字段，`render` 只认识占位符，`storage` 只认识路径。界面与命令行都调
这里，避免两套命名规则各写一遍。

## 2. 命令

```bash
# 1) 先有模板。真实模板属受控材料不入库，仓库里给一份合成模板
python tools/make_demo_template.py

# 2) 出文书（同时写台账）
python -m cedas render "判决书.pdf" --date 2026-10-31 --effective-date 2026-11-15

# 3) 只看结果不落盘
python -m cedas render "判决书.pdf" --dry-run

# 4) 机器可读
python -m cedas render "判决书.pdf" --json
```

| 参数 | 作用 | 现场用法 |
| :--- | :--- | :--- |
| `--doc-type` | 选映射表（`执行通知书`） | 后续文书面世时加映射表即可，不改代码 |
| `--defendant` | 只出某个被告人，可重复 | 同案多人分别送达时 |
| `--start-date` | 人工指定起算日 | 判决书与强制措施段都取不到时 |
| `--effective-date` | 判决生效日（C 组录入） | 主文未载起止日的案件（实测 53%） |
| `--date` | 文书日期（落款 + 文件名） | 补出历史文书时必须显式给 |
| `--dry-run` | 组装上下文不落盘 | 复核界面预演 |
| `--allow-missing` | 核心字段缺失仍生成（降级） | **仅应急**，报告会标 `degraded` |
| `--no-db` | 不写台账 | 重出某份文书、不想加版本 |

退出码：`0` 全部成功；`1` 存在阻断项。脚本可据此判断，不必解析中文输出。

## 3. 起算日：两级来源，且来源必须可见

这是整个链路里最容易被悄悄做错的一步。优先级从高到低：

| 优先级 | 来源 | 触发条件 | 依据 |
| ---: | :--- | :--- | :--- |
| 1 | 人工指定 | 传了 `--start-date` | 办案人员裁定，最高优先 |
| 2 | 判决书载明起止日 | **尚未实现**（C 组 `text_start_end` 未抽取） | 需先补齐 C 组 |
| 3 | `calc.resolve_start` | 有期徒刑/拘役取羁押起始日；管制取判决生效日 | 刑法 41/44/47 条、刑诉法 76 条 |
| 4 | 阻断 | 以上都取不到 | 报 `E-START`，不出文书 |

报告里的 `start_source` 字段会写明这一份用的是哪一种（`人工指定` / `羁押起始日` / `生效日期`），
界面必须原样显示——复核的人要能一眼看出「这份的起算日是推出来的还是人定的」。

> 为什么第 3 条不是「猜」：`08-公开语料与真实文书回归` 统计了 36 份真实判决主文，
> 19 份（53%）根本不写起止日，只写「刑期从判决执行之日起计算」。这类案件的起算日
> 只能来自生效日期，是 C 组必须人工录入的字段，而非系统的自由裁量。

## 4. 阻断与降级

阻断判据只用「有没有值」，不用「值准不准」——准不准由复核界面与人负责。

| 码 | 含义 | 处置 |
| :--- | :--- | :--- |
| `E-CASE-NO` | 案号缺失 | 阻断：归档路径无从生成 |
| `E-COURT` | 法院名称缺失 | 阻断：文书落款错 |
| `E-NAME` / `E-GENDER` / `E-BIRTH` / `E-ID` | 被告人身份四项缺失 | 阻断：看守所据此收人 |
| `E-CHARGES` | 罪名缺失 | 阻断 |
| `E-PRINCIPAL` / `E-TERM` | 主刑或刑期未识别 | 阻断：算不出届满日 |
| `E-START` / `E-END` | 无起算日 / 无届满日 | 阻断：先录生效日期 |
| `W-START-EFFECTIVE` | 起算日按生效日期推得 | 放行，报告标注 |
| `W-NO-EFFECTIVE` | 生效日期未录入，文书该处留空 | 放行，报告标注 |
| `W-COMBINED` / `W-PROBATION` | 数罪并罚 / 缓刑案件 | 放行，口径待业务方确认 |
| `W-DEGRADED` | 用了 `--allow-missing` | 放行，报告标 `degraded=true` |

**为什么宁可不生成**：一份缺身份证号的执行通知书送到看守所，退回重做的时间成本远高于
当场补录；更糟的是没人会怀疑它——占位符已被替换成空白，看起来像「本来就没这项」。

## 5. 归档与版本

```
{归档根}/（2023）京0105刑初123号/张三/（2023）京0105刑初123号_张三_执行通知书_20261031.docx
                                                                    └─ 重出时 → _v2_20261031.docx
```

- 非法字符 `\ / : * ? " < > |` 换成 `-`，保留名（`CON`、`LPT1`…）前缀加 `_`
- 单段超过 60 字符截断，整体路径超过 250 字符**报错不截断**（截断后的路径可能指向另一份文书）
- 版本号在渲染**前**探测，`v2`、`v3` 递增，旧件永不覆盖——法院要可追溯，不是最新版

## 6. 台账

`documents` 表记 `rel_path` + `sha256` + `version`。哈希的作用不是校验内容正确，
而是回答「盘上这份文件还是台账记的那份吗」：文书被人挪走、改过、覆盖，一比对就知道，
不会静默指向一个已经变了的文件。

## 7. 合成模板

模板来自法院、属受控材料，`.gitignore` 已排除 `resources/templates/*.docx`。
但没有模板，这条链在开发机与 CI 上都跑不起来，因此提供
`tools/make_demo_template.py` 生成一份**合成模板**：

- 版式与真实模板同构：标题、案号、正文、逐格填写的表格、落款
- 首行带「示例 · 合成 · 不得作为司法文书使用」，不会被误当正式文书
- 只用段落与简单表格，不含内容控件、域代码、SmartArt（目标机办公软件版本低）

```bash
python tools/make_demo_template.py          # 生成
python tools/make_demo_template.py --check  # 校验占位符与映射表是否一致
```

`--check` 回答一个具体问题：**模板里的占位符集合与映射表声明的字段集合是否一致**。
不一致有两种后果，都很难在生成后肉眼发现——映射表声明而模板没用到（该处永久空白）、
模板用了而映射表没声明（渲染直接抛 `UnresolvedPlaceholderError`）。

替换成真实模板的步骤：

1. 把法院给的 `.docx` 放进 `resources/templates/`（或 exe 旁的 `resources/templates/`）
2. 改映射表里的 `template` 字段指向它
3. 跑一次 `--dry-run`，看有没有占位符未解析
4. 若报未解析而模板里明明有：**占位符被 Word 拆成了多个 run**（01 §3.7），
   删掉整段重新一次性输入

## 8. 还没解决的

| 缺口 | 影响 | 备注 |
| :--- | :--- | :--- |
| 法院真实模板未验证 | 占位符兼容性未知 | 唯一无法用合成数据替代的风险 |
| C 组 `text_start_end` 未抽取 | 判决书载明的起止日没被用上，一律按强制措施段/生效日推 | 应先于「真实模板」做，能减少对生效日录入的依赖 |
| 管制折抵的羁押天数未传 | 管制案件的届满日会偏后 | `compute_span(custody_days=...)` 已支持，缺的是「羁押天数」这个录入项 |
| 缓刑 / 数罪并罚 / 单位犯罪 | 只标告警不特殊处理 | 见 `08` §4.4、§4.5 与真值表「待确认口径」 |
| 并发写同一目录 | 无锁，两份进程可能抢同一版本号 | 单机单人场景可接受，多进程部署前必须加 |
| 界面未接数据流 | 只能命令行出文书 | `ui/` 仍是空窗口，接 `pipeline.generate()` 即可 |
